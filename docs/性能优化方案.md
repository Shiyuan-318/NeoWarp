# NeoWarp 性能优化方案

> 版本：v1.0 ｜ 适用版本：NeoWarp 2.0.0（Electron 41 / TurboWarp scratch-gui develop）
> 本文档仅制定方案，不包含具体代码实现。

---

## 一、现状概述

NeoWarp 是基于 TurboWarp/scratch-gui 的 Electron 桌面应用，整体架构为：

- **主进程**（`src-main/`）：入口 `entrypoint.js → index.js`，24 个窗口模块，约 20 个自定义协议；
- **预加载层**（`src-preload/`）：23 个 preload 脚本，sandbox + contextIsolation 已统一开启（做得好）；
- **渲染层**：`src-renderer/` 下 20 个手写静态页面（不经 webpack），`src-renderer-webpack/editor/` 为唯一经 webpack 打包的部分（scratch-gui 主界面）。

### 当前主要性能瓶颈（按影响排序）

| # | 问题 | 位置 | 影响 |
|---|------|------|------|
| 1 | 编辑器主 bundle 16.4MB 未做代码分割，每次开窗（含 SOLO 隐藏宿主）全量解析 | `dist-renderer-webpack/editor/gui/index.js`、`webpack.config.cjs` | 窗口打开慢、内存占用高 |
| 2 | SOLO 模式用隐藏的完整 EditorWindow 做 VM 宿主，且 8fps PNG 帧流常开 | `editor.js:1294`、`desktop-hoc.jsx:188-207`、`solo.js:412` | CPU/内存双重浪费、后台节流进一步限帧 |
| 3 | 舞台帧流为 WebGL readback → PNG dataURL → 两段 IPC，detach 30fps / SOLO 8fps | `desktop-hoc.jsx:152-207`、`detached-stage.js:102` | 每帧几十~几百KB base64，三进程拷贝、GC 压力大 |
| 4 | `themeInterval` 每秒轮询 localStorage 且从不清理，随 locale 切换累积 | `desktop-hoc.jsx:4461` | 定时器泄漏、长期运行退化 |
| 5 | AI web-search 最多约 8 个请求完全串行，单个超时 15s | `ai-assistant.js:153-278` | 最坏 90s+ 才返回 |
| 6 | 协议层 brotli 资源每次请求重新读盘解压、无缓存 | `protocols.js:354-363` | library/extensions 加载重复消耗 CPU |
| 7 | 20 处同步 IPC + `pbkdf2Sync`（10 万次 sha512）阻塞主进程事件循环 | 各 preload、`editor.js:115/143` | 开窗卡顿、加解密时全局冻结 |
| 8 | `ai-assistant.html` 578KB 单文件（7500 行内联脚本），三处共用；`phone-sync.js:190` 每次请求同步读该文件 | `src-renderer/ai-assistant/` | 解析慢、主进程同步 IO |
| 9 | 所有窗口共用 `session.defaultSession`，无 partition 隔离 | `abstract.js` | 缓存/存储互相干扰，安全隐患 |
| 10 | sourcemap（15MB+ 的 .map）未从安装包排除 | `package.json` build.files | 安装包体积膨胀 |

### 做得好的地方（保持）

- 工程保存走 MessagePort + atomic write stream 背压；
- library 文件清单只 readdir 一次并缓存；
- 协议层有路径穿越防护；
- AI 工具调用有超时与 listener 清理机制。

## 二、优化目标（可度量）

| 指标 | 现状（估算） | 目标 |
|------|------------|------|
| 编辑器窗口冷启动到可交互 | 3–6s（16MB bundle 解析） | ≤ 1.5s |
| SOLO 模式内存占用 | 约等于完整编辑器实例 | 降低 40%+ |
| 舞台帧流 CPU 占用（detach 30fps） | 高（base64 + 双跳 IPC） | 降低 50%+ |
| AI web-search 最坏耗时 | 90s+ | ≤ 25s |
| library 资源重复请求解压次数 | 每次请求 1 次解压 | 进程生命周期内每文件 ≤ 1 次 |
| 安装包体积 | 含全部 sourcemap | 剔除 dev 产物，减小 15MB+ |
| 主进程事件循环最长阻塞 | pbkdf2Sync 百毫秒级 | < 16ms（一帧） |

---

## 三、优化方案（分模块）

### 3.1 构建与打包（收益最大，优先做）

**3.1.1 编辑器 bundle 代码分割**
- 在 `webpack.config.cjs` 中配置 `optimization.splitChunks`：将 `node_modules`（scratch-vm、scratch-render、React 等）拆为独立 vendor chunk，将 addons 与 l10n 拆为异步 chunk；
- 开启 `runtimeChunk: 'single'`，保证 chunk hash 稳定、可长期缓存；
- 为 `babel-loader` 开启 `cacheDirectory`，缩短增量构建时间；
- 评估将 webpack 4 升级到 webpack 5 的可行性（持久化缓存、tree-shaking 更强、产物更小），若升级成本过高，至少在 webpack 4 下完成 splitChunks 配置。

**3.1.2 产物清理**
- electron-builder 的 `files` 中排除 `*.map`、`!**/*.map`，确保 dev 构建的 sourcemap 不进安装包；
- 将 `src-renderer/extension-editor/vs/`（Monaco 24MB）改用 monaco-editor 官方 webpack 插件按需打包（只保留用到的语言与 worker），或改为 `asarUnpack` + 按需加载；
- `dist-library-files`（41MB .br）保持 asar 外（`asarUnpack`），避免协议层读取 asar 内大文件的额外开销。

**3.1.3 死代码清理**
- 删除无引用的 `src-renderer/ai-assistant/ai-assistant.js`（77KB 死文件）；
- 将 `ai-assistant.html` 的内联样式与脚本拆分为独立文件并开启缓存，578KB 单文件拆分后首开解析时间可显著下降。

### 3.2 渲染进程（编辑器核心体验）

**3.2.1 修复 themeInterval 泄漏（P0 bug）**
- 将 `desktop-hoc.jsx:4461` 的 `setInterval(checkThemeChange, 1000)` 纳入 `componentWillUnmount` 统一清理（参照已有的 `_flyoutFrostInterval` / `_topBarStatsInterval` 清理模式）；
- 更优方案：用 `storage` 事件或自定义事件总线替代每秒轮询 localStorage，彻底消除轮询。

**3.2.2 舞台帧流传输改造**
- 现状：WebGL readback → PNG dataURL → 主进程 → 目标窗口，base64 字符串跨三进程；
- 方案（按改造成本从低到高）：
  1. **降本**：PNG 改 JPEG/WebP（`canvas.toDataURL('image/jpeg', 0.7)`），体积降 60%+；detach 帧率 30fps 可配置化；
  2. **去字符串化**：改用 `ArrayBuffer`/二进制 IPC（Electron 26+ 支持结构化克隆二进制），去掉 base64 编解码；
  3. **治本**：SOLO/分离舞台改用同窗口内嵌或 `webContents` 共享纹理（offscreen rendering），彻底消除跨进程帧拷贝；
- SOLO 帧流改为**按需开启**：仅当 solo-stage 窗口可见时启动，隐藏/最小化时暂停（结合 `document.visibilityState` 与窗口事件）。

**3.2.3 顶栏统计与磨砂效果降频**
- `get-system-stats` 由每 2s 一次改为每 5s，且仅在窗口聚焦时轮询；主进程侧缓存 `os.cpus()` 结果（CPU 型号不变，只需采样负载）；
- flyout 磨砂 300ms interval 已有清理，可进一步改为事件驱动（菜单打开时启用、关闭时停）。

### 3.3 SOLO 模式与隐藏宿主

**3.3.1 轻量化 VM 宿主（中期重构）**
- 现状：`editor.js:1294 openHidden` 创建完整隐藏 EditorWindow（16MB bundle + 完整 GUI）仅为运行 scratch-vm 供 AI 工具调用；
- 方案：抽出一个"headless VM 宿主"页面——只加载 scratch-vm + scratch-render（或纯 VM 无渲染），不加载 GUI/addons/l10n，bundle 体积预计从 16MB 降至 3–5MB；
- 过渡方案（先做）：隐藏宿主窗口关闭 backgroundThrottling（`webContents.setBackgroundThrottling(false)`），避免 VM 帧循环被降频影响 AI 工具与帧流。

**3.3.2 AI 助手单例绑定修正（正确性兼性能）**
- 现状：`AIAssistantWindow.show(B)` 只聚焦已有窗口，工具仍作用于编辑器 A；
- 方案：AI 窗口与编辑器实例建立显式绑定关系（Map<editorId, aiWindow>），或切换聚焦编辑器时重定向工具目标并刷新上下文，避免错误目标导致的无效工具往返。

### 3.4 主进程与 IPC

**3.4.1 消除同步阻塞**
- `pbkdf2Sync`（10 万次 sha512）改为 `crypto.pbkdf2`（异步）或迁移到 worker_threads/utilityProcess，加解密 .npnp 时不再冻结主进程；
- 20 处 `sendSync` 逐步改为 invoke/handle 异步模式；其中 `is-initially-fullscreen` 在 React render 路径中同步调用（`gui.jsx:22`），建议在窗口创建时通过 query 参数或 `additionalArguments` 传入，渲染层零 IPC 获取；
- `set-locale` 不再同步回传整张翻译表，改为异步事件推送 + 增量更新。

**3.4.2 协议层缓存**
- `tw-library` / `tw-extensions` 的 brotli 解压结果加 LRU 缓存（按文件路径 + mtime 作 key），同文件进程生命周期内只解压一次；
- 高频小文件可考虑预热：编辑器打开后后台空闲时预解压常用 library 素材；
- `getWindowByWebContents`（`abstract.js:94`）的线性扫描改为 `Map<webContents.id, window>` 直接索引——它被 session 级 webRequest 钩子在**每一次网络请求**时调用，O(n) → O(1) 收益稳定。

**3.4.3 窗口与 session 隔离**
- 按窗口类别划分 session partition（如编辑器 / AI 助手 / SOLO 各用独立 partition），隔离缓存与 storage，避免互踩；
- 窗口模块改为懒加载：`index.js` 启动时只 require 必需模块，其余在首次打开对应窗口时动态 require，缩短启动时间。

**3.4.4 phone-sync 同步读文件**
- `phone-sync.js:190` 每次手机请求都 `fs.readFileSync` 读 578KB HTML：启动时读一次缓存内存（文件在 asar 内不会变），或改异步读 + 缓存。

### 3.5 AI 助手链路

**3.5.1 web-search 并行化与预算控制**
- 现状：DDG → Bing → DDG API → 双 Wikipedia → 抓 top3 正文，全串行，最坏 90s+；
- 方案：
  1. 搜索引擎查询并行发起（Promise.any/Promise.allSettled），首个可用结果即返回；
  2. top3 正文抓取并行；
  3. 设置**总时间预算**（如 20s）与降级策略：超时即返回已有部分结果；
  4. 结果按查询哈希做短时缓存（5–10 分钟），避免重复搜索。

**3.5.2 AI 工具响应通道去重**
- 现状：AI 窗口既被全局 `ipcMain.on('project-json-response')` 直接 resolve，又收到 editor 转发的 `project-code-response`，存在双通道重复投递；
- 方案：统一为一条通道（保留 editor per-frame 转发，去掉全局监听），减少一次主进程消息分发与潜在竞态。

**3.5.3 CDN 运行时依赖本地化**
- pdf.js 等运行时从 cdnjs 动态加载（`ai-assistant.html:9937`）：打包进本地资源，离线可用且消除网络抖动；
- 收紧 CSP，移除对 `cdn.jsdelivr.net` / `cdnjs.cloudflare.com` 的放行（本地化后不再需要）。

### 3.6 启动流程

- l10n 的 `generated-translations.json`（168KB）按需加载：启动只加载当前语言，其余语言在切换时加载；
- GitHub 更新检查（15s 超时）保持异步，但延迟到首个窗口 `ready-to-show` 之后再发起，不占用启动关键路径；
- `settings.js` 的同步 `readFileSync` 保留（文件小、启动期单次），但 `settings.save()` 增加防抖（短时间多次设置变更合并为一次写盘）。

## 四、实施路线图

### 第一阶段：低风险高收益（1–2 周）
1. 修复 themeInterval 泄漏（3.2.1）— P0 bug；
2. 排除 sourcemap、清理死文件（3.1.2 / 3.1.3）；
3. 协议层解压缓存 + `getWindowByWebContents` 索引化（3.4.2）；
4. web-search 并行化 + 时间预算（3.5.1）；
5. phone-sync 文件缓存（3.4.4）；
6. SOLO 帧流按需启停 + JPEG 编码（3.2.2 第 1 档）。

### 第二阶段：结构性优化（2–4 周）
1. webpack splitChunks 配置（3.1.1）；
2. 同步 IPC 异步化改造、pbkdf2 移出主进程（3.4.1）；
3. 隐藏宿主关闭 backgroundThrottling、AI 单例绑定修正（3.3）；
4. AI 响应通道去重、pdf.js 本地化（3.5.2 / 3.5.3）；
5. 帧流改二进制 IPC（3.2.2 第 2 档）。

### 第三阶段：深度重构（4 周以上，需评估）
1. headless VM 宿主替代隐藏完整编辑器（3.3.1）；
2. session partition 隔离（3.4.3）；
3. webpack 4 → 5 升级评估；
4. Monaco 按需打包（3.1.2）。

## 五、验证与度量

每项优化落地前后需用统一方法度量，避免"凭感觉优化"：

1. **启动耗时**：主进程 `process.uptime()` + 渲染层 `performance.timing`，记录从 app ready 到 `ready-to-show` / `did-finish-load` 的时间；
2. **内存**：任务管理器窗口（已有 `task-manager` 模块）记录各进程 `getProcessMemoryInfo`，对比开窗前后 RSS；
3. **帧流开销**：在 IPC 收发两端打点，统计每秒字节数与消息数；
4. **主进程阻塞**：用 `event-loop-lag` 类探针（或手动 `setInterval` 漂移测量）监控事件循环延迟，重点验证 pbkdf2 改造效果；
5. **回归测试**：每次改动后跑通核心路径——打开工程、运行、保存、AI 工具调用、SOLO 模式、分离舞台、打包导出。

## 六、风险与注意事项

- **代码分割**可能改变 chunk 加载顺序，需重点回归 addons 与 l10n 的初始化时机；
- **session partition 隔离**会清空各窗口现有 localStorage/缓存数据，需做迁移或提前告知用户；
- **headless VM 宿主**改动面大，AI 工具的 60+ 个接口依赖完整 VM 环境，需逐一验证快照类工具（现有 180s 超时机制可复用）；
- **pbkdf2 异步化**涉及加解密流程的调用方全部改为 await，注意 .npnp 文件打开路径的错误处理；
- 所有改动保持与上游 TurboWarp/scratch-gui develop 分支的可合并性，定制集中在 `desktop-hoc.jsx` 与 `src-main/`，避免直接修改 scratch-* 包内代码。
